```
$ logs grep 'NullPointerException' --since 2026-10-30T06:50:03Z --until 2026-10-30T07:19:24Z
2026-10-30 06:50:03.130 ERROR ... NullPointerException ...

$ logs grep 'NullPointerException' --since 2026-10-30T06:49:00Z --until 2026-10-30T06:51:00Z
...
2026-10-30 06:49:59.119 ERROR ...
2026-10-30 06:50:03.130 ERROR ...        ← 同一条，是 A 的最后一次

$ logs first 'order 2 loaded for user 9999' --since 2026-10-30T06:50:00Z
2026-10-30 06:50:14.773 INFO  ... order 2 loaded for user 9999   ← 兜底第一次成功
```

容器启动时刻（`Started TargetServiceApplication`）：**06:50:13.089**。
所以 06:50:03.130 那条 NPE 是**旧容器（实例 A）的最后一条**，
它在 06:50:03.667 的重建之后仍短暂服务了 0.4 秒，被切进了 B 的桶。

根因：桶边界取自**症状时间戳**（最后一次 NPE = 06:50:03），而不是**容器启动时刻**。
披露口径：「实例边界按症状时间戳切分，实例 B 的那 1 次 NPE（06:50:03.130）
实际属于实例 A——B 的容器 06:50:13.089 才启动，兜底首次成功是 06:50:14.773；
B 段实际零 NPE，报告的方向反而更强。」

### D5（小项）台阶的带宽写窄了

报告 §2 写「形态为台阶 **8.2–8.9%**」。实测 60s 步长比例：

| 区间 | 比例 |
| --- | --- |
| 06:06–06:50（实例 A） | 8.000% – **9.259%** |
| 07:20（过渡桶，C 刚起） | 5.752% |
| 07:21–07:36（实例 C） | 8.228% – 8.917% |
| 07:55–07:57（实例 F 刚起） | 7.865% – 8.750% |

**形态判断（台阶、非尖刺、非缓增）完全正确**，且比 10-27 那一轮的平台更平。
只是写的带宽比实测窄：实测平台是 **8.125–9.259%**（06:06–06:50 与 07:21–07:36），

## 4. 这一轮暴露的、属于**实验室侧**的缺陷（不是这轮报告的错）

### L1（最重要）改写服务仓库历史，把两次真实的「缺陷上线」从 Agent 眼前抹掉了

详见 §2.6。危害有三层：

1. **Agent 被迫去解释一个不存在的问题。** 它提出「需补的证据：CI 构建日志或镜像 digest」，
   而这个证据实验室自己就有（manifest + bundle）。这会让报告显得「有未解之谜」，
   而实际上谜底是自造的。
2. **报告少写了一整个模式**：同一个缺陷 blob（`34e92a3`）被部署 → 修回 → 又被部署回去。
   这正是 F2 场景最值得展示的东西，也是这轮报告【处置建议】第 3 条摸到边但没写透的东西。
3. **可复核性受损。** 复核者如果只在当前仓库里查，就永远查不到 `486fb57` / `f24ecb8`。

**处置建议**（注意：**不能**简单地「把归档 ref 放回仓库」）：

- ❌ **不可行**：在服务仓库里放 `refs/lab-archive/failed-f2-*`。ref 名里就带 `f2`，
  Agent 一条 `git log --all` 就看见了；`$LAB git log` 虽然是 HEAD-only，
  但 Agent 有 shell，`git log --all` 是它会做的动作。这比现在更糟。
- ✅ **可行的最低限度**：
  1. 归档 bundle 留在 `~/incident-lab-archive/`（现状），
     **并且 `incident/RESUME.md` 里显式记下「本轮观察窗可能混有前几轮的容器活动」**——
     这句话现在没有，是本轮冒出「未解释项」的直接原因。
  2. 复核件里出现「实例 X 当时的 HEAD 与日志矛盾」这类判断时，
     **先去查 `round-manifest-*.json` 的 `injection.at` / `injection.commit`**，
     再决定是不是真的矛盾。本轮我先去查了 `git log --all`，差点把它写成服务侧谜团。
  3. 如果以后要让 Agent 自己也能解释这一段，唯一不泄漏的做法是
     **把「前几轮注入 → 修回」的提交用中性 ref 名（如 `refs/archive/prior-1`）保留**，
     且提交信息本身不带故障标签（现有提交信息符合这条）。**但这会改变 F2 的难度**
     （Agent 会看到同一 diff 反复上下线），属于基准设计决定，不能顺手做。
- **在修好之前，任何跨轮次的「发布史」结论都不可信**——包括复核者自己的。
  本轮的 `git log` 只能证明「0738Z 这一轮看到的是什么」，不能证明「当时真实部署过什么」。

`channel-audit.mjs` 判 `out_of_surface: 9`、`contaminating: 0`，与我的独立复核一致。

### L3 `logs` 的时间窗只作用于带时间戳的行，栈帧续行被窗口查询排除
