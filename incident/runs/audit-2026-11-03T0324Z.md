### D1（硬错，且是工具面引发的）「9.9% 的瞬时高点」不是观测值，是**查询未来时间戳**造出来的伪影

报告【反对证据】第 3 条写：

> 5xx 比例观测到 9.9% 的瞬时高点（03:42:45 一带）略高于 8.5% 平台值，
> 归因于 1m 窗口边界与总流量 2.46–2.91 rps 的抖动，不影响结论。

**这里叠了两层错：**

**第一层：位置错了。** 9.9% 不在 03:42:45，而在 **03:43:20**（时间戳 1793677400）。
Agent 自己那条 `metrics range` 的原始返回里：

```
[1793677360, "0.08333333333333333"]   ← 03:42:40  8.33%
[1793677365, "0.0846153846153846"]    ← 03:42:45  8.46%
...
[1793677400, "0.09999999999999999"]    ← 03:43:20  10.0%   ← 它引用的那个数在这
[1793677405, "0.07142857142857142"]    ← 03:43:25   7.14%
```

03:42:45 那一格是 **8.46%**，不是 9.9%。

**第二层（更要紧）：这个 10.0% 根本不是那一时刻的比例。**
那条命令是

```
metrics range '<5xx 比例表达式>' 2026-11-03T03:38:00Z 2026-11-03T03:46:00Z 5s
```

**end 是 03:46:00，而命令执行时刻约在 03:42:37**——range 的后半段整体落在**未来**。
Prometheus 对未来的步点做 `rate(...[1m])` 时，窗口里只有「到执行时刻为止」的样本，
窗口被截断，于是比值退化成**小整数比**：1/12、11/130、5/58、3/34、1/11、**1/10**、1/14…
0.09999999999999999 就是 1/10（17/170 之类），不是「这一秒里 10% 的请求是 5xx」。

**判据：同一条查询在「已过去」的步点上，我逐点重算的结果与 Agent 当时的返回完全一致**——
从 03:41:10 到 03:42:35，**18 个点逐个相等**（1.287%、1.945%、…、8.552%、8.491%、8.228%、8.75%、8.75%）。
分叉点恰好是执行时刻之后的第一个步点 **03:42:40**。

**真实值**（02:50–03:50 全窗、5s 步长）：

| 项              | 实测                                                            |
| --------------- | --------------------------------------------------------------- |
| 平台区间        | **8.075% – 8.917%**                                             |
| 全窗最大值      | **8.917%（03:43:30）**                                          |
| 03:43:20 实际值 | **8.75%**（按原始计数器手算：5xx 增量 15 / 总增量 174 = 8.62%） |
| 出现过 9.9% 吗  | **没有**（全窗没有任何一个点 > 9.0%）                           |

**结论方向**：报告用这条来说「略高于 8.5% 平台值」——**方向反了**。
真实峰值 8.917% 确实略高于 8.55%，但报告引的 9.9% 是虚高的，
而且「03:42:45 一带」这个定位本身是错的。**根因结论不受影响**
（它出现在【反对证据】里，用途是解释一个并不需要解释的小波动）。

### D2（过度声称）平台值写作「8.2%–9.9%」

实测平台是 **8.075%–8.917%**（§3-D1 表）。上沿 9.9% 无任何观测支撑（见 D1）；
下沿写 8.2% 也略高于实测的 8.075%。
**形态判断（台阶而非尖刺/缓增）完全正确**，只是带宽两端都写错了。

### D3（过度声称）「`/profiles` 404 速率故障前后完全一致（0.2545/s 不变）」

实测（60s 步长）：

| 时刻        | 404 速率                             |

**处置建议**（按可行性排序）：

1. ✅ **最低限度**：下一轮的 Agent 指令面里明确写死「证据面之外的东西不读」，

   **代价**：真值不再随仓库走，评审方要另取一份；

### L2 `metrics range` 可以把 end 设到未来，返回**用截断窗口算出来的伪影值**

机制与 D1 相同，但这是**工具面的坑**，不是 Agent 的错：
命令语法上完全合法，返回的 JSON 也完全合法，只是尾部的值没有物理意义。

**处置**：在 `tools/incident-readonly.mjs` 的 `metrics range` help 里写明

比值会退化成 1/10、1/12 这类小整数比，看上去像尖峰，实际不存在」。
**在工具把这件事写明白之前，任何人（包括复核者）都会踩。**
（与 0738Z 那条 L3——`logs` 的时间窗只作用于带时间戳的行——是同族的：都是「工具语义不说清」造成的误读。）

### L3 注入提交在轮后被**从服务仓库里剪掉并 gc 掉**

F2 的 `restore()` 只把 order 2 移出压测路径，**不把代码改回去**——
这是有意的（缺陷要留着，下一轮再注入一次）。但跑完一轮，服务仓库就多一条注入提交；
轮次一多，服务仓库的历史就会堆成一串「缺陷上线下线」，既污染 Agent 看到的 `git log`，
也让复核者分不清哪条是哪轮的。

**本轮的处理**（已完成，可复核）：

```
$ git bundle create ~/incident-lab-archive/round-f2-0324z.bundle refs/tmp/archive-f2-0324z
$ git update-ref -d refs/tmp/archive-f2-0324z && git reset --hard 7bb726a
$ git reflog expire --expire=now --all && git gc --prune=now
$ git cat-file -e 35fb5a3   →  致命错误: Not a valid object name（已剪掉）
$ git bundle verify ~/incident-lab-archive/round-f2-0324z.bundle  →  完整历史
```

即：**注入提交完整保存在仓库外的 bundle 里，仓库回到基线 `7bb726a`，对象已被 prune。**
§2.2 的全部复核就是从这个 bundle 取回原始提交做的。

**遗留**：0738Z 那轮的 L1 已经指出「把归档 ref 放回服务仓库」不可行（ref 名会泄漏 F2）。
本轮的做法（bundle 留在仓库外 + reset + gc）是目前最干净的一种，
但**bundle 的路径必须写进 RESUME**，否则下一轮找不到注入提交就复现不出来了。

## 7. 补记：本复核件自己推翻过的三条结论

按「自己的错也得说」的原则记在这里，因为它们已经在过程中被我写下并差点写进本文件：

1. **「报告的 NPE 30 次多写了一半，实测是 60」——错。**
   根因：我用了朴素行数 grep。**一次 NPE 事件在日志里占 2 行**
   （`Servlet.service() …` + `java.lang.NullPointerException: …`）。
   按 `Servlet.service()` 计是 30，按去重时间戳计也是 30。**报告的 30 是对的。**
2. **「报告把 order 1 写成 29 是漏数」——错。**
   根因：我用 `>= 03:41:10` 的窗口切，而 order 1 的成功加载落在 03:41:09.869（早 0.131s）。
   **报告的 29 是对的**，只是它的窗口左边界把这个负载切掉了。
3. **「本轮 Agent 只列了名字、没读任何内容」——错。**
   根因：我写 §4-L1 时凭印象下了结论，**没回 transcript 逐条对**。
   实际第 3 次调用 `cat ../agent-profile/*` **读到了 `identity.json` 的内容**
   （Agent 自己的 prompt，6259 字节）——§2.6 当时就记着这件事，是 §4 写岔了。
   **答案键确实一次没读**（这条结论不变），但「只列了名字」是错的。
   同时 §2.6 里「打印 6 个历史报告文件名」也少算了：实际是 **11 份历史 .md + `RESUME.md`，
   共 12 条**。

前两条指向同一件事：**用「一条 grep 的输出」下结论之前，先确认那条 grep 的语义**
（grep 数的是行，事件数要去重时间戳；窗口边界会吃掉边缘事件）。
第三条指向另一件事：**同一份文件里的两节互相矛盾时，要回头查原始记录，而不是挑顺眼的那节**——
§2.6 与 §4 对「Agent 读没读到东西」的记载本来就不一致，我写的时候没对。
这也是 0738Z 那份复核 §7 已经记过一次的两条教训——**同一个坑，两轮都踩**。
