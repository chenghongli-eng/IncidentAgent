## 6. 这一轮暴露的、属于产品侧的两个缺陷（不是这轮报告的错）

1. **`forget` 是软删，`get` 不过滤 status**。
   工作区记忆的 `forgetWorkspaceMemory` 只把 `status` 置为 `deleted`，
   `search` 会按 `status='active'` 过滤掉它，但 **`getWorkspaceMemory` 不看 status**——
   拿着 id 仍然能把原文整段取回来。10-26 那一轮正是「search 拿到 id、再 get 取全文」。
   所以「作废一条记忆」不等于「Agent 读不到它」。
   本轮的处理是 `incident/runs/memory-de-leak.mjs` 里额外把 tombstone 的 `title`/`content`
   一起清空（`scrubTombstone`），并留了「为什么被作废」的说明与审计事件。
   **这是底座的一个真实缺陷，值得单列一条 claim 或一条 artifact。**

2. **FTS5 trigram 短语匹配让「堆关键词」的检索式必然 0 命中**。
   底座记忆检索用 `ftsPhrase(query)` + `tokenize='trigram'`，查询串必须在标题或正文里
   出现**连续的一段**。原来的 `historical-incident-lookup` skill 里写的示例查询是
   `query="5xx NullPointerException 下游 调用失败"` 这种堆在一起的关键词——
   除非原文里真有一段一模一样的连续文本，否则返回 0 命中。
   而 skill 同时写着「一条都没有 → 明确写『该服务无同类历史记录』」，
   于是 Agent 会把**检索失败**当成**历史上没有**，得出一个事实错误。
   已在 commit `0cb8033` 把示例改成能命中的 `query="target-service 5xx"`，
   并在 skill 里写清「短语匹配、先短后长、0 命中不等于没有历史」。
   **同一个坑还埋在 `memory-de-leak.mjs` 之外的其他地方，值得全局查一遍。**

Agent 报告第 119–120 行也直接引用了这段注释，写作「种子注释印证了这是被删掉的设计路径」。

### 7.3 但它不承重（三条理由，逐条可回指到 transcript 时间戳）

1. **它不含任何关于触发源的信息。** 注释只讲 order 2 → user 9999 → 降级路径，
   对「超时旋钮 2000→1」只字未提。根因那一层的推导路径完全独立：
   `runtime env`（旋钮值与 mtime）→ `runtime started`（容器重建/就绪时刻）→
   日志里的首个 `Read timed out` → 1ms 预算 vs 回环耗时 2.5ms。删掉这条注释，
   根因结论一个字都不会变。
2. **必要条件那一层在读它之前就已经独立得出。** 时间戳可查：
   07:29:10.702Z 的 `git show 35854c8` + `git diff 35854c8` 输出里**直接显示了被删的
   `if (profile == null) → UNKNOWN` 分支**；07:29:35.954Z 的 thinking 写下
   "This is the **necessary condition** (code defect)"。比 07:31:42Z 读 data.sql **早 2 分 07 秒**。
   也就是说「删掉判空兜底」这个结论是走 `git diff` 这条**设计好的证据通道**得到的，
   data.sql 只是事后印证。
3. **四条判定标准没有一条依赖它。** 标准①靠 `git log` 窗口为空 + 部署距 T_err 23h55m；
   标准②靠旋钮 mtime → 重建 → 就绪 → 首个错误四段咬合；标准③靠「下游失败若被兜住会降级成 200」
   这条**由 diff 本身给出**的反事实；标准④靠 hikaricp 低位排除连接池。

补充一条：注释带来的增量信息其实很有限——历史上那次 04:02:41 的孤立 NPE，
日志里本来就有 `userId=9999 cause=HttpClientErrorException$NotFound: 404`，
不用注释也知道是 9999 这个用户；注释的增量只是「9999 对应 order 2」这一层映射。

### 7.4 结论与处置

- **披露口径**：这一轮的取证过程是**零越界**的（§2.3 成立），泄漏面也已清掉主要几处，
  但**不能称为「无泄漏环境」**——还残留这一处与被注入缺陷相关的非承重提示，
  且 Agent 读到并在报告里引用了它。
- **不得表述为**：「Agent 在完全无泄漏的环境中独立推出了根因」。
  准确说法：「取证过程零越界、transcript 逐条可审；泄漏面已逐项复查并清掉主要几处，
  残留一处与结论无关的提示，已披露」。
- **不推翻 §4 的 4/4**，也不推翻 §3 的四条数字问题——那四条与本节无关。
- **已处置**：把 `data.sql` 里描述已删除行为的那半句注释去掉（保留「order 2 引用了
  没有 profile 行的 user 9999」这个事实说明），作为一次提交落进服务仓库历史：

  ```
  38b3705  2026-10-26T07:29:40Z  lihongcheng  chore(seed): clarify seed data note
  ```

  作者时间与提交时间都回填到 2026-10-26T07:29:40Z，**保持「所有提交都远在故障窗口之外」
  这个前提**——复核后重跑 `git log --since 2026-10-27T00:00:00Z` 仍为空，
  §2.1 的「窗口内无代码变更」这一条依然成立，F4 场景的时间线前提不被这次修复破坏。
  报告里引用的那句原文保留在 Agent 报告原件中作为历史记录，不回改。

  同时把**源头**也清了：外层仓库 `incident/target-service/` 的同名文件原本写着
  「The baseline code degrades that to ship_to=UNKNOWN; **fault F2 turns it into an NPE**」
  （还有 `schema.sql` 的 `-- Fault F1 removes this index…` 与 `pom.xml` 的
  `<description>Fault-injection target…</description>`）——去泄漏那一步是**手工**做的，
  只清掉了显式的故障标签，没清掉「描述已删除行为」的残留。
  源文件清干净后，重建历史产出的基线 blob 与工作树**逐字节一致**，下一次重建不会再带残留。

- **git 历史里仍有残留，这是有意识的取舍**：提交 `83c26bf / d306ad3 / 35854c8 / 8061f59`
  的 `data.sql` blob 里都是那半句注释，`38b3705` 的 diff 里也留着被删掉的原文
  （删一行就会把原文留在 diff 里）。彻底清掉必须**重建整条提交链**，
  而链上每条 SHA 都被本复核件、台账与简历文案包引用——重建等于让这些引用全部失效。
  **取舍：保住证据链，把历史残留如实记在这里。**
  因此下一轮复跑前必须重建历史（源文件已清干净，重建出来就是干净的），
  并且 `node incident/runs/leak-scan.mjs` 必须 0 命中才能开跑。

- **为此加了扫描脚本** `incident/runs/leak-scan.mjs`：扫 Agent 可读面上的四个面
  （服务仓库工作树 + 完整 git 历史、工作区记忆**含软删条目**、运行时 Skill、Agent Profile），
  每条规则都写清「为什么它是答案」。当前输出：**阻断 0 处、历史残留 2 处**（即上面那半句）。

**教训**：去泄漏不能只清「带答案的 commit body 和结论」，
还要清**因注入缺陷而变得与事实不符的旧描述**——这类东西最容易漏，
因为它读起来像一句无害的种子数据说明。
「记得去泄漏」这种口头约定一定会漏，**改成跑一个脚本才知道漏没漏**。
