## 3. 报告里的三处问题（数字错误 / 口径错误 / 假象）

### 3.1 D1（硬错误）：锚点 ② 引了一个产出不了该值的命令

报告的锚点表里写：

> ② 首个异常 `2026-11-04T03:41:43.467 Read timed out` ← 出处标注为
> `logs first 'Read timed out' --since 2026-11-04T00:00`

我重跑了这条命令，**它返回的是 `2026-11-04T03:18:23.859`**，不是 03:41:43.467。
transcript 里那次调用的原始输出（以及我现在重跑的结果）完全一致。

也就是说：**引用的命令与引用的值对不上**。值本身是对的（`03:41:43.467` 确实是首个故障时刻的
Read timed out，见 §2.1），但报告给读者留了一个**复现不出该值的"出处"**。

同样的问题还有一处：报告另一处引 `logs first 'threw exception' --since 2026-11-03`，
该命令返回 `2026-11-03T03:41:02.561`（**前一轮**的 NPE），而不是本轮的 03:41:43.472。

**这是第 3 次撞上同一类错误**（前两次：0827Z 轮、11-03 F2 轮，都是"引了一个不产出该值的命令"）。
**处置**：

- 报告原件不改（本复核件即为更正记录）；
- 诊断口径必须以**值**为准，本轮的值经我复核全部正确；
- **F4 轮必须用 `--since` 限定到本轮故障窗口**（本例应写 `--since 2026-11-04T03:41:00`），
  否则 `first` 类命令天然会捞到上一轮的记录——这是工具用法的坑，要写进工具的提示词或 README。

### 5.2 为什么说 F4-C1 / F4-D1 是判据的锅

**F4-C1**：v5 的 pattern 要求「触发源/根因/机制 … **运行时旋钮|超时旋钮|运行时配置|配置层**」或镜像。
报告写的是「运行时把下游读超时压到 1 ms」——**这在语义上完全正确**，
但词表里「运行时旋钮」「运行时配置」「配置层」都是**名词枚举**，
「运行时**把**…**压到**…」这种**动词化的动作描述**不在其中。
报告里唯一接近的是「运行时生效值」——而 v5 的 `near_miss_wording`
**故意**把「生效值」列为 near-miss（= 需要人复核，不能自动算命中）。

→ **这正是「判据量的是措辞，不是诊断能力」的第四例**（前三次：v2→v3 的 markers、v3→v4 的层级词、v4→v5 的 `near_miss_wording`）。
→ v6 必须**扩充命中面**，但**不能**简单把「生效值/运行时参数/超时预算」提为命中——
那正是 `near_miss_wording` 存在的意义（这些词单独出现时**不足以**断定 Agent 找到了配置层的原因）。

**F4-D1**：4 种备选措辞**全部**要求「触发源/触发因/根本原因」这类层级词，或要求写在表格的 `|` 管道里。
报告写的是「发布变更无关：排除」——**这是人话、而且语义正确**，
但它既没用层级词，也没排在表格里。
→ 排除类判断本来就不该要求层级词（层级词是用来**命名**原因，不是用来**否定**原因的）。
→ v6 应给排除类单独一套措辞（例如「发布/上线/变更 … 无关|排除|不是原因|非触发源」），
且**保留「需与同窗内的正确归因并列」的约束**，避免"只要写了排除就算数"的刷分路径。

**Q2 不在这次修改范围内**：层级词表**故意不含「机制」**（0827Z 那轮起就定了），
Q2 的 FAIL 是 Agent 没做分层——这与 F4-C1 的情况**不同**：
F4-C1 是**该说对了但词没在表里**，Q2 是**该说两层但只说了一层**。**Q2 不放宽。**
