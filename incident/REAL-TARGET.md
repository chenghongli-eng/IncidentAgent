# 接入真实项目作为靶子

## 为什么必须做这一步

现在台子里唯一的服务是 `target-service/`：一个 Spring Boot 夹具，
一个 `OrderService`、一个方法、三个合成故障。**这个分布是我想象的**，
真实世界的故障长什么样，我其实没有把握。

更关键的是复杂度差了一个量级：靶子里 Agent 只需要在一个文件里找一行代码；
真实项目里它要在几百个文件、十几个模块里定位。这两件事不是同一个难度，
合成靶子上测出来的能力，**不能外推**。

所以这一步不是"锦上添花"，是**把实验从玩具变成真东西**。

## 先说没有 Jira 的问题：不影响

方案之前提过"接 Jira 拿发布记录"。**没有 Jira 完全可以做。**
部署锚点本来就不该只依赖工单系统——工单是**人写**的，代码和运行时是**机器记**的，
后者更可靠。三个锚点都能从你已有的东西里取到：

| 锚点             | 没有 Jira 时从哪来                                         | 可信度     |
| ---------------- | ---------------------------------------------------------- | ---------- |
| **告警起始**     | Alertmanager `activeAt` / Prometheus 告警规则求值时刻      | 高（机器） |
| **异常首次出现** | 应用日志里第一条异常的时间戳（Agent 有 `logs first` 通道） | 高（机器） |
| **部署时刻**     | 见下                                                       | 中高       |
| **部署改了什么** | 构建号 → commit 的映射（**部署台账**），见下               | 中         |

部署时刻有四个互相印证的来源：

1. **进程/容器启动时间**：`process_start_time_seconds`（Prometheus 侧）
   或 `runtime started` 通道（容器重建时刻 + 应用就绪时刻）。
   这是**硬事实**：进程什么时候起的。
2. **Git 提交时间**：如果发布流程是"拉某个 commit 构建"，
   那么 commit 的 committer date ≈ 镜像构建时间 ≈ 部署时间（差几分钟）。
   `git log --since` 拿到的就是这个。
3. **镜像 tag / digest**：如果能拿到部署的制品标识，和 commit 一一对应就闭环了。
4. **应用自己的启动日志**：`Started XxxApplication in N seconds` 这行的时刻。

四条对上，就是一个**有界窗口**（不是精确时刻）。而部署归因判定本来就不需要精确时刻：
现有 Prompt 里的规则是 `T_dep ≤ T_err ≤ T_dep + 15min → 高度相关`，
`T_err > T_dep + 15min → 排除`——**窗口足够**。这正是当初刻意选"窗口"而不是"时刻"的原因。

### 部署台账：把「构建号 → commit」变成机器可读

现场核查（2026-11-05）确认：k8s 清单里的 `<BUILD_TAG>` 是 **Jenkins 构建号**，
**不是 commit sha**，且三个候选项目**都没有** `git-commit-id` /
`build-info-maven-plugin`——**应用没法自己报出它跑的是哪个 commit**。

所以「这次部署改了什么」这一环需要一条独立的映射：

```
镜像 tag（构建号） ──部署台账──> commit sha ──git──> 改动内容
```

台账文件放**仓库外**（和答案键、工作区同一条规则），由 `incident-readonly`
的一个**只读通道**读取——**不新建一个联网通道**，CLI 保持只读、离线可复现。

> **来源的排序后来改了**：主数据源**不是 Jenkins**，而是「集群实际在跑的镜像 digest
>
> - Registry 的 OCI label」，Jenkins 降级为可选富化源（理由见下）。
>   读侧也**不是** `git` 通道，而是新增的 `deploy` 通道——`git` 通道只认 commit，
>   而台账要回答的第一件事是「现在跑的是哪个 digest」。

台账缺条目时必须**明确报错**，不能退化成「窗口内无代码变更」：
这两件事对 Agent 的意义完全相反（一个是"排除了发布"，一个是"没查到"）。

所以：**没有 Jira 不构成阻塞。** 需要人工提供的只有一条信息：
「这个项目的发布是怎么发生的（拉哪个分支/哪个 tag、谁触发、构建产物怎么标识）」。
这句话能从同事那问出来，不需要系统对接。

#### 台账的设计已经写完（2026-11-05）：`incident/DEPLOY-LEDGER.md`

上面这段问题陈述之后的方案在 **`incident/DEPLOY-LEDGER.md`**。
核心结论与上文**一处不同、两点补充**：

- **一处不同**：台账主数据源**不是 Jenkins**。
  Jenkins 记的是「构建了什么」，集群记的是「跑着什么」，两者可能不一致
  （构建成功但发布失败、发布的不是这次产物、回滚）。
  主源应当是**集群实际在跑的镜像 digest + Registry 的 OCI label**，
  Jenkins 降级为**可选富化源**（构建结果、耗时、触发人、节点）。
- **两点补充**（实测得来的，不是推理）：
  1. **Registry label 这个源今天不存在**——12 个项目的 Dockerfile
     **全部 0 条 `LABEL`**。所以它是**一次构建流水线的一行改动**，
     不是"接一下就能用"的现成数据源。
  2. **台账的主键是 digest**（今天就有，pod 的 `imageID` 直接给），
     commit 是**补上去的**。时间戳窗口只用来"是不是这次发布"的关联，
     不能用来确定"是哪个 commit"。

台账仍按上文原则放在**仓库外**、由 CLI **只读文件**读取，
不新建联网通道——联网和持凭据的部分在**采集器**里，在 Agent 可达范围之外。

**读侧已经实现并验证**（2026-11-06，阶段 1，控制脚本 39/39）：`incident-readonly` 的 `deploy` 通道
（`current` / `lookup` / `running` / `list` / `check`），缺条目与非容器锚点都**硬报错**，
**短 digest 前缀查得到、前缀有歧义时报歧义**，新鲜度与答案**在同一份输出**里。
控制脚本 `incident/runs/deploy-ledger-control.mjs`。
**阶段 0 也已完成**：一条**真实**台账条目已建（仓库外 JSONL，
字段全部来自 `docker inspect` 与 git HEAD），读侧 `check`/`lookup`/`current` 全部命中。

**写侧（阶段 2 的 registry 段）也已实现并验证**（同日，采集器控制脚本 29/29）：
`incident/collector/collect-registry.mjs` 匿名读 registry，拿 digest / 构建时间，
按 git 历史关联 commit，**追加**仓库外的 JSONL。
三条与"归因"直接相关的纪律写进了代码而不是文档：

- **一行一条观测，不是一个镜像一行。** 同一 digest 重新部署、或事后被确认在跑，
  都是新观测，会被追加；只有**同一 digest 的矛盾事实**（两个构建时间 / 两个 commit）
  才拒写报错。按 digest 去重会静默丢掉"已经跑了多久"。
- **`commit_reliable` 默认 false。** 只有 `oci-label` / `annotation` 算可靠；
  `git-window` / `git-head-fallback` / `manual` 一律不可靠，输出里带"只能当线索"。
  **这不是保守**：真实镜像里的 jar 与本地**任何 ref** 都对不上（见 `DEPLOY-LEDGER.md` §12.6），
  即"查到了 commit"**不等于**"知道镜像里的代码"。Agent 不得据不可靠 commit
  读源码并断言"这就是当时在跑的代码"。
- **`deploy running` 回答"现在跑的是哪个"，并写出出处。**
  人工确认记为 `running_source: human`，与集群观测的 `k8s` 并列；
  它与 `pod_started_at` 是**两个事实**，前者不冒充后者。

**写侧又接上了 CI 段与 cluster 段**（2026-11-06 深夜，见 `DEPLOY-LEDGER.md` §13）：
「构建号 → commit」**不再靠时间推断**——构建号就是 tag，
CI 的构建记录里 `lastBuiltRevision.SHA1` 就是这次构建**实际检出**的 commit；
集群只读（Rancher 的 Kubernetes 代理，**不需要 kubectl**）给出 `pod_started_at`
与运行中的 `imageID` digest。实测 6 个构建号**全部**拿到 CI 来源的 commit，
本地 git 推断降级为 `commit_inferred` 保留在行里；
同时实测出 git 推断有多不可靠（`git-window` 3/3 对，`git-head-fallback` **1/3 对**，
根因是本地 clone 陈旧）。

**但这一步同时暴露了设计的两个缺口**（详见 `DEPLOY-LEDGER.md` §11.3）——
**它们比台账本身更重要，且都在采集器开工之前必须处理**：

1. ~~**`commit` 与 `digest` 的绑定没有机器凭据**（`commit_source: "manual"`）。~~
   12 个候选项目的 Dockerfile **全部 0 条 LABEL**，
   所以在真实靶子上人工填是**默认状态**：
   **OCI label 落地之前，部署归因给出的 commit 只能当线索，不能当事实。**
   → **2026-11-06 深夜部分解除**：CI 的构建记录是一个**已有的机器凭据**
   （`jenkins-build`，权威等级与 OCI label 同级），不需要改 Dockerfile。
   仍未解除的部分：Dockerfile 里**仍然 0 条 LABEL**，
   所以「镜像自述」这条最硬的凭据还没有；只是现在有了一条**次硬但真实存在**的。
2. ~~**台账主键 `digest` 在宿主进程形态的靶子上不存在**~~
   → **2026-11-06 傍晚解除**：宿主形态的主键取**产物文件自身的 sha256**
   （`sha256:<64 hex>`，与镜像 digest 同一形态，读侧不需要第二条查找路径——
   实测 `deploy lookup <digest>` 命中 `matched_on='digest'`）。
   落地在 `incident/collector/host-target.mjs`，对照组 **35/35**：
   与系统 `sha256sum` 对拍、已知值 `sha256("abc")`、>1MB 分块边界、
   进程不在时启动时刻为 null、与 `ps -o etimes=` 交叉核对（drift < 2s）。
   启动时刻取 `/proc/<pid>/stat` 第 22 字段 + btime + CLK_TCK，
   **取不到就是 null，绝不编**；只有看得见的进程才带 `running_observed_at`。
   → **2026-11-09 解除：真实靶子的宿主形态真的采过一行了**（见下）。

#### 真实靶子的第一行台账（2026-11-09 实测）

P2 的 `java -jar` 实例（`127.0.0.1:12306`，只绑回环、把所有 cron 推到
「一月一日」——它连的是共享的开发库，**不许**让它自己跑定时任务）跑了一次
`incident/collector/host-target.mjs`，仓库外的台账里多了一行：

| 字段             | 值                                | 说明                      |
| ---------------- | --------------------------------- | ------------------------- |
| `digest`         | 产物自身的 sha256（值留在仓库外） | 宿主形态没有 image digest |
| `artifact_kind`  | `file`                            | 自包含的胖 jar            |
| `evidence`       | `host-artifact-sha256`            | 主键是怎么算出来的        |
| `pod_started_at` | **实测**的进程启动时刻            | 不是手写的                |
| `running_source` | `host`                            |                           |
| `commit`         | `null`，`commit_source='null'`    | 见下——**故意是空的**      |

读侧复核全部命中：`deploy lookup <digest>` → `matched_on='digest'`；
`deploy running` → 来源 `host`；`deploy current` → 命中、delta 0 秒、
`anchor_source` 写着 `host process (pid …, port …)`。

三件事是这次实测**逼出来的**，不是设计出来的：

1. **部署单元可能是目录**。CI 构建出来的那份产物是「瘦 jar + `lib/` 目录」
   （276 个文件，173MB），不是单个文件。用单文件 sha256 标识它，
   `lib/` 变了主键也不变——那就等于把两次不同的部署认成一次。加了**内容
   寻址的 tree hash**（按相对路径排序、拼接每个文件的内容哈希、根路径不
   参与），`digest` 的形态不变，读侧不需要第二条查找路径。
2. **启动锚点必须实测**。读侧原来信 descriptor 里手写的 `startedAt`，
   那对真实靶子是**四天前**的值——读侧会去读一个四天前的日志窗口，然后
   报告「台账里没有这次部署」，而台账里明明有那一行。现在锚点优先取
   **活进程的实测启动时刻**；都取不到就**拒绝**，并把那个手写值一起报出来
   当证据（「我用的是 descriptor.startedAt，它是 …」≠「查不到」）。
3. **`commit` 那格故意空着**。这份产物是本地构建的，工作区里可能有未提交
   的改动，本地 git 推断出来的 commit 只是一个线索。填上它，台账就声称了
   一件它没有证据的事。CI 构建出来的那份才有 `jenkins-build` 来源的 commit。

细节在 `incident/DEPLOY-LEDGER.md` §16。

#### 第二行台账：CI 构建出来的那份产物（2026-11-10 实测，A2）

A2 要的不是「本地构建的那份产物」，而是 **CI 构建出来的那份部署单元**
（瘦 jar + `lib/` 目录，276 个文件）。理由在 `DEPLOY-LEDGER.md` §16：
本地工作区里可能有未提交改动，本地 git 推断出来的 commit 只是一个**线索**；
只有 CI 那份产物才配得上 `commit_source='jenkins-build'`（权威等级与
OCI label 同级）。把那个 commit 挂到本地构建的胖 jar 上是**错的**。

实测做法：按仓库外的启动规格跑 CI 制品（启动目录在部署单元**之外**，
这样运行时的日志不会写进部署单元、tree hash 不会漂），
再用 `collector/host-target.mjs --commit <CI 构建记录的 commit>
--commit-source jenkins-build` 采一行。台账里多出来的这一行：

| 字段                  | 说明                                                      |
| --------------------- | --------------------------------------------------------- |
| `digest`              | 部署单元的 **tree hash**（值留仓库外）                    |
| `evidence`            | `host-artifact-tree-sha256` + `proc-start-time`           |
| `commit`              | CI 构建记录里的 commit（**值留仓库外**）                  |
| `commit_source`       | **`jenkins-build`**（不是 `git-window`，也不是 `manual`） |
| `pod_started_at`      | 实测的进程启动时刻                                        |
| `running_observed_at` | 实测的观测时刻                                            |

**这一行解决的是什么**：真实项目镜像的 Dockerfile 里 **0 条 LABEL**，
所以「镜像自述 commit」这条最硬的凭据还没有；在它落地之前，
`jenkins-build` 是**次硬但真实存在**的一条。归因时能说
「这次运行的是哪一次 CI 构建」，而不是「本地 HEAD 推的」。

**它没有解决什么**：它不改变「真实靶子的 commit 只能到 `jenkins-build`
这一档」这个结论（B1 仍未解除）。`commit_reliable` 对这一档是 `true`，
但档位本身仍然是「CI 构建记录」，不是「产物自述」。

## 真正需要先解决的是合规，不是 Jira

这里有一件必须先想清楚的事，比技术方案重要：

> **Agent 读到的每一行代码、日志、指标，都要送到模型那里。
> 你现在的 provider 是 deepseek / MiniMax 这类第三方 API。**
> 如果靶子是公司的真实项目，**代码就离开公司了**。

这不是"注意一下"级别的事，是"整个实验的前提"级别的事。分三档看：

| 档位  | 模型在哪                                                                   | 代码出不出内网 | 适合什么                     |
| ----- | -------------------------------------------------------------------------- | -------------- | ---------------------------- |
| **A** | 内网自建推理服务（vLLM / Ollama / SGLang，OpenAI 兼容接口）                | **不出**       | **公司真实项目**             |
| **B** | 第三方 API，但只喂脱敏后的事实（指标值、异常堆栈、提交摘要），**不喂源码** | 半出           | 真实项目但降级到"只读事实"   |
| **C** | 第三方 API，代码直接进 prompt                                              | 全出           | **只用于合成靶子和开源项目** |

现在的状态是 C。**对合成靶子和开源项目，C 完全没问题**；
对公司的真实项目，至少要 A。

Miniclaw 这边接一个本地 OpenAI 兼容端点只是**改 Provider 配置**，
不需要改 Agent 逻辑——这正是当初把 Provider 做成配置项的回报。
需要准备的只有：一台能跑得动的机器 + 一个够格的模型 + 一个评测结论
（**小模型在长链路诊断上的表现，是这套方案最大的未知数**，得实测，不能假设）。

### 档位 A 的落实情况（2026-11-05）

公司在内网自建平台上部署了 minimax 模型，走公司内网地址，配置由公司自己设置
（平台名与地址见仓库外）。**「机器 + 模型」这一项已具备，档位 A 成立。**

剩余三项待验证，都不是设计问题，是配置问题：

- [x] 端点是否 **OpenAI 兼容**（Miniclaw 的 Provider 配置依赖这一点）
- [x] 模型是否支持 **tool calling** 与 **streaming**（Pi runtime 的工具循环依赖它）
- [x] 开发机能否**直连**该内网地址

**三项已于 2026-11-05 实测通过**（见 `incident/RESUME.md` 的 provider 小节）：
该内网端点**只挂 Anthropic 协议**（`/v1/chat/completions` 返回 404，
**不影响** Miniclaw——它说的就是 Anthropic 协议），tool calling 返回 `stop_reason: tool_use`，
SSE 流式完整，CA 已在系统信任库里。⚠️ 原配置的模型名对该 key 是 **403 不可用**，
已换成 `MiniMax-M2.7`；默认 provider 已切到内网。
**代价是模型队列分裂**：合成靶子那 4 轮有效证据属于 deepseek 队列，
内网队列**目前 0 轮有效证据**（第一次基线轮中止在 429 配额上）。

⚠️ 换 provider 会**分裂模型队列**：合成靶子那 4 轮有效证据属于 deepseek 队列，
内网模型是另一个队列，两者不能放进同一张「谁更强」的表比。
新模型下的第一件事是**补一轮基线**，不是直接进真实靶子。

## 推荐路径：先回放，再注入，最后才谈真实事故

不要一上来就往真实服务里注入故障。分三步，每步都能独立产生价值：

### 第 0 步：回放历史故障（**最该先做的一步**）

找 1–2 个**已经发生过、已经修好**的真实故障。Agent 不做任何注入，
只拿"当时的告警 + 当时的日志 + 当时的指标 + 当时的代码状态"做复盘，
看它能不能查出和当时人查出的**同一个结论**。

好处非常实在：

- **不需要破坏任何东西**，零风险
- 有**人写的正确答案**做对照（当时那个工单/复盘文档），
  比合成靶子的判据可信得多
- 这是**回放**，不是实验，能反复跑、能改、能比较
- **一次回放的价值 > 一百次合成靶子轮次**

难点：需要"当时的现场"——旧日志、旧指标、旧代码版本。
日志可能已经滚掉了；Prometheus 通常只保留几天或几周；代码能靠 Git 回到那个 commit。
**关键是要趁早动手**，趁这些现场还在的时候把回放素材抓下来存档。
这一点有**时效性**，越晚做越做不了，建议排在最前面。

### 「一次故障要分析很多次」怎么满足：采集一次，回放多次

一个真实故障的现场（告警 + 指标窗口 + 日志片段 + 当时的代码状态 + 部署锚点）
应当被**归档成一份可重复使用的场景包**，而不是每次重新制造故障：

| 场景包字段         | 用途                                          |
| ------------------ | --------------------------------------------- |
| 告警与告警时刻     | 起点锚点                                      |
| 指标查询与窗口     | 排除证据的复现依据（PromQL 原样存档，可重跑） |
| 日志片段与时间窗   | 异常首次出现、栈顶方法                        |
| 当时的 commit 集合 | 部署归因的可比范围                            |
| 人类结论           | **对照答案**（回放式评测的"真值"来源）        |

有了场景包，同一个故障可以换模型、换 Prompt、换判据**反复跑**，
每次都得到可比的结论——这正是合成靶子用「反复注入」换来的能力，
而在真实靶子上它**零风险**、**无限次**、而且对照的是**人写的真值**。

三类日志素材的分工（详见 [REAL-TARGET-SURVEY.md](REAL-TARGET-SURVEY.md) 的「答复二」）：
**生产日志**提供真实分布与人写的结论；**测试环境（Rancher）**提供部署产物，
是唯一能练「部署归因」的地方；**本地开发旧日志**提供噪声与信号混杂的语料，
但没有部署锚点。三者是互补，不是替代。

### 第 1 步：只读体检（不注入任何故障）

让 Agent 对真实项目做一次**健康体检**：当前有什么指标、有哪些已知风险点、
最近的变更是什么、哪些依赖是外部的。不注入、不破坏。
目的是验证**观测通道搭得对**：Prometheus 有没有接对、日志能不能查到、
`git log` 能不能拿到、指标名对不对。

这一步会暴露最多"环境没配好"的问题，而这些问题在合成靶子上永远不会出现。

#### P2 体检的执行结果（2026-11-05）

靶子：**P2**（项目名、制品名与应用名见**仓库外**的映射表）。目标不是评分，是**通道体检**：
六条通道逐条打通，且每条都用的是真实项目的数据。

搭台子的三个决定，都记在这里，因为换个人来做会踩同样的坑：

| 决定                    | 做法                                                                                            | 为什么                                                                                                               |
| ----------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **不复用 IDE 那个进程** | 另起 `java -jar <服务>.jar`，端口 12306，cwd `/mnt/my-work/incident-lab/targets/p2`             | IDE 里那个实例（12305）是用户自己的，参数不该由我们改；另起实例才可复现（启动命令见 `targets/p2/start-target.sh`）   |
| **只绑回环**            | `--server.address=127.0.0.1`                                                                    | 体检实例会连**共享的 dev 库**（PostgreSQL / Redis），不该对内网暴露成一个能被人随手调的服务                          |
| **Prometheus 单独一个** | `prometheus-real`（host 网络，127.0.0.1:9094），只抓 `127.0.0.1:12306`                          | 合成夹具那 4 轮有效证据依赖 `:9090` 的历史数据；两个 Prometheus 混在一起等于动量具                                   |
| **写库的定时任务关掉**  | `auto.subtask.scheduler.*` / `rubric.supervise.extract.cron` 全部改成 `0 0 0 1 1 ?`（永不触发） | 体检期间不希望这个实例往共享 dev 库写子任务。唯一写死的 `ScheduleLogTask` 是 `0 0 1 * * *`，本月不会触发             |
| **Redis 换库**          | `--spring.redis.database=15`                                                                    | 目标项目有一个 `@Scheduled(fixedDelay=1000)` 的消费者，会从 **共享** Redis 队列里 `rightPop`——不隔离会把别人的活抢走 |

**通道体检结果**（全部通过）：

| 通道          | 结果                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `target info` | 描述文件解析正确（靶子/指标标签/别名/三条地址/仓库/日志目录）                                                                                                            |
| `metrics`     | ✅ **PromQL 里的 `application="target-service"` 被自动改写成 `application="<目标应用>"`**（stderr 打印 effective query），查得到真实数据（`jvm_memory_used_bytes` 有值） |
| `actuator`    | ✅ `health` 返回真实状态（PostgreSQL UP / Redis UP / 磁盘）                                                                                                              |
| `logs`        | ✅ 目标项目的日志格式（`2026-11-05 08:30:43.512 [thread] LEVEL logger - msg`）能解析；`--count` 不重复计数                                                               |
| `git`         | ✅ 读的是目标项目真实仓库历史（`<commit-sha>` 等）                                                                                                                       |
| `runtime`     | ✅ 靶子不是容器时，锚点回落到描述文件的 `startedAt`                                                                                                                      |

**过程中改了两处产品本体**（不是为体检临时打补丁，是真实靶子必然遇到的缺口）：

1. **actuator 通道支持认证**。真实靶子的 actuator 几乎都在鉴权后面。
   新增 `ACTUATOR_TOKEN`（直接放进 `Authorization` 头）或
   `ACTUATOR_USERNAME` + `ACTUATOR_PASSWORD`（Basic）。
   **凭据只从环境变量读，不进描述文件**——描述文件是可以被复制的，凭据不该跟着它走。
2. **`runtime started` / `runtime env` 不再因为"不是本地容器"就报错退出**。
   靶子是宿主进程时，锚点回落到描述文件的 `startedAt`，`runtime env` 明确打印
   「container_env: (unavailable)」而不是假装读到了。

**顺手发现并记下的一条**：目标项目的 dev 配置里 `<artifactId>.security.mock-enable=true`，
意味着 `Authorization: <mockSecret><用户号>` 就能以任意用户身份通过鉴权。
这是**公司项目自己的开发配置**，不是我们开的口子，但生产必须关掉——
这一点值得在接入真实项目时和团队确认一次。

**体检没做到什么**（边界要写清楚）：

- 这一步**没有评分**。真实项目还没有对应的故障注入夹具，
  现在跑出来的报告只能证明"通道通"，不能证明"诊断得准"。
- T_dep 这一环**仍然缺**：目标项目没有 `git-commit-id`，应用报不出自己的 commit。
  体检实例的启动时刻是**我们**知道的，不是从部署台账推出来的——
  真实场景里这一环要靠台账（见上面的「部署台账」一节）。
- 这一步**没有碰生产**，也**没有碰共享 dev 库里的业务数据**（只读 + 定时任务关闭）。

#### 真实靶子的第一轮 dry-run（2026-11-09）

`runs/run-round.mjs` 以前只会打**合成夹具**：前置闸门问的是「三个容器在跑吗、
挂载源在工作区吗、日志在长吗」。这三个问题在真实靶子上**一个都不成立**
（真实靶子是宿主进程、空闲时日志不增长、没有容器挂载）。

所以轮次编排现在支持 `--target <描述文件>`，走另一套前置闸门
（实现见 `runs/target-preflight.mjs`，负对照见 `runs/target-preflight-control.mjs`）：

| 闸门 | 问什么                                    | 为什么合成夹具那套问法在这里不成立                                       |
| ---- | ----------------------------------------- | ------------------------------------------------------------------------ |
| P1   | 证据通道在位                              | 换成这个靶子的 Prometheus / actuator / 日志目录 / 部署台账四个地址       |
| P2   | 日志通道**由靶子自己持有**                | 目录里有日志文件 ≠ 靶子在写它；看的是进程的文件描述符（写句柄）          |
| P3   | 靶子**在自己的指标里**现身                | 活性信号用「指标在」，不用「日志在长」——真实靶子空闲时日志一个字节都不长 |
| P4   | 基线 5xx 比例 = 0                         | 同一个 PromQL，只是标签值换成靶子自己的                                  |
| P5   | 开跑前没有告警在 firing，**且必须有规则** | 没有规则时「没有告警在 firing」是空话，闸门看着是绿的，其实什么都没证明  |

实测结果（P2 靶子，dry-run）：**五条全绿**，P12 的 provider 探测报
「接得住一轮规模」（约 5 万 token 的一次真实请求），manifest 里
`dry_run: true` + `round_valid: false`——按设计，dry-run **不是一轮成绩**。

这一轮顺带逼出了三个真实环境的问题，都已处理：

1. **真实通道的 Prometheus 一条告警规则都没有**。那时候 P5 只能写成
   「没有告警在 firing」，而这句话什么都没证明。现在给它加载了与合成夹具
   同口径的 5xx 比例规则（规则文件与配置都在**仓库外**），P5 才成立。
   顺带发现真实靶子**没有暴露延迟直方图**（只有 `_count`/`_max`，没有 `_bucket`），
   所以夹具那边那条 P99 告警在这个靶子上**不存在**——照抄会得到一条永远不
   firing 的规则，看起来像「延迟没问题」，其实是「这条告警在这个靶子上没有」。
2. **描述文件的日志目录已过期**：它指向的是上一次跑靶子的位置，
   而当前进程写的是另一个目录。按描述文件去读，会读到一份**停在最后一次
   启动**的旧日志，而且读起来毫无异样。现在 P2 把这件事**说出来**，
   并且按**实测**目录覆盖 `LOG_DIR` 交给 Agent（描述文件本身要改，
   那是仓库外的文件，改它需要单独授权）。
3. **轮次产物不进仓库**。真实靶子的 manifest 落在仓库外的归档目录里：
   它讲的是真实项目，而仓库是公开的。

**这一轮没有证明什么**（边界写清楚）：

- **没有注入故障**。真实靶子的轮次现在**只允许 `--dry-run`**：没有故障的
  一轮不是成绩，它只是证明台子能跑起来。真实项目的注入手段是第 2 步的事。
- **工作区还是合成夹具的工作区**（里面是夹具的源码，不是靶子的仓库）。
  真实靶子轮次要换成靶子仓库的工作区，那是第 3 步的事。
- P12 的探测**只能**证明「provider 接得住一轮的上下文」，不能证明额度够跑完整轮。

### 第 2 步：可逆注入（真实代码上做最小改动）

在**本地或隔离环境**（不要在生产）跑起来的真实项目副本上，
做一处**可逆**的改动——改一个配置值、加一段可控延迟、改一个超时。
然后跑一轮完整诊断。

比合成靶子强的地方：Agent 要在真实代码结构里定位，
真实依赖（Redis、MQ、DB）的影响是真的，观测信号是真的。

### 第 3 步：真实故障复盘

等第 0 步的回放和第 2 步的可逆注入都跑通了，
再考虑在隔离环境模拟一次接近真实的事故。

**这一步之前不要碰生产环境。**

## 接入一个真实项目需要准备什么

一张清单，逐项确认：

- [x] **能本地起**（或起一个隔离副本）。**2026-11-05 确认：所有候选项目本地都能跑。**
- [ ] **有 Prometheus 指标**。Micrometer / actuator 最好；没有的话先接。
      **注意**：这批公司项目的 actuator 端点**默认全是关的**
      （`management.server.port: -1` 或 `endpoints.enabled-by-default: false`），
      但 `micrometer-registry-prometheus` 依赖都在。
      本地跑时用三个环境变量就能开，**不需要改源码**——
      详见 [REAL-TARGET-SURVEY.md](REAL-TARGET-SURVEY.md) 的「发现一」。
      目标：至少 `http_server_requests`（按 uri/status）、JVM、连接池、GC
- [ ] **有结构化日志**，且带时间戳、级别、异常栈。
      **2026-11-05 确认三处来源**：生产主机（代号见仓库外，可复制）、
      测试环境 Rancher（好拿）、本地开发旧日志（P1 已有 147.6MB）
- [x] **有 Git 历史**，且历史深度足够（能回到故障发生时的版本）。
- [ ] **知道发布是怎么发生的**。**2026-11-05 部分答复**：Jenkins 构建 → 镜像 tag
      = **构建号**（不是 commit sha），k8s 清单 `<内部制品库>/<服务名>:<BUILD_TAG>`。
      **仍缺**：构建号 → commit 的映射（部署台账，见上）。
      **2026-11-06 进展**：台账读侧已验证，且已有一条真实条目；
      **当晚补上**：构建号 → commit 已由 **CI 构建记录**机器给出（不再是推断），
      集群只读也通了（`pod_started_at` 有机器来源，`running_source: k8s`）。
      **仍未解决**：Dockerfile 里仍 0 条 LABEL（没有「镜像自述」这条最硬的凭据），
      且宿主进程形态的靶子**连 digest 这个主键都没有**（见上）
- [x] **确认合规档位**（A/B/C）。**2026-11-05 确认为 A**：
      内网自建平台上有 minimax 模型，走公司内网地址，配置由公司自己设置。
      OpenAI 兼容 / tool calling / 开发机可达**三项已于 2026-11-05 实测通过**
- [ ] **确认授权范围**：哪些仓库、哪些环境、故障可以注入到什么程度
- [ ] **确认观测通道**：现有 `tools/incident-readonly.mjs` 的命令要能映射到
      新靶子的实际路径和指标名（这一步通常要改 CLI，**只加不改**：现有命令语义不要动）

## 改造点预估

`tools/incident-readonly.mjs` 现在把路径和指标名**硬编码**了
（`application="target-service"`、固定日志目录、固定 git 仓库路径）。
接真实项目要把它改成**从一份靶子描述文件读取**，例如：

```
incident/targets/<name>.json
{
  "application": "your-service",
  "repoPath": "...",
  "logsDir": "...",
  "prometheusUrl": "...",
  "extraPromql": { ... }
}
```

这样**靶子变成配置而不是代码**，新增一个真实靶子不用改 CLI、不用改编排脚本。

这是接真实靶子之前应该做的**唯一一处结构性改造**，
其余（判据、闸门、通道审计）都跟靶子无关，可以原样复用。

## 与现有台子的关系

- **合成靶子保留**。它是回归集，是 CI 里的快速闸门，是防止本体改坏的安全网。
- **真实靶子新增**，作为**能力上限的证明**和**真实分布的来源**。
- 判据要分开写：合成靶子的判据（`ground-truth/F2.json` 等）冻结；
  真实靶子用**回放式对照**（人的结论 vs Agent 的结论），不必套用同一套正则判据。
