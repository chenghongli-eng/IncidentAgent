### 1. 缺陷 1：指标表读不了脱敏后的路径（`round-table.mjs`）

manifest 里的路径在提交时做过脱敏（绝对路径 → `<repo>` / `<home>`），
表却拿它当文件路径用，于是 `score=null` → 每一轮都判成「未跑完（中止或 dry-run，没有报告）」。
修法是逐个候选解析：原样 → 剥掉占位符按仓库根解析 → 按 `incident/runs/` 下的文件名解析；
全部落空才返回 null（表示「这个面没拿到」，而不是默默当成没有）。

### 2. 缺陷 2：leak-scan 少扫两个面（`leak-scan.mjs`）

原来扫的面里没有**聊天历史**和 **Pi 会话记录**。这两个面恰好装着上一轮的答案：
上一轮的提问与根因报告原文在 `messages` 表里，上一轮的完整对话（提问 + 工具调用 + 报告原文）
在 `data/sessions/<folder>/.claude/sessions/*.jsonl` 里。`run-round.mjs` 每轮开跑前会清它们，
所以**闸门运行时它们必须是空的**。

新增的两个面用**结构性判据**：非空即阻断，不靠关键词。理由是可测的——
0738Z 那份**完全正确**的报告从头到尾写的是「null 保护」，`F2` 一个字都没出现，
关键词表对它一个都命中不了。所以关键词只能当线索，阻断判据只能是「空 / 非空」。
这条判据也写进了 `leak-scan.mjs` 的文件头注释。

**负对照**（`node incident/runs/leak-scan-control.mjs`，4/4 通过，全部在副本上跑）：

| 对照     | 构造                       | 期望                           | 实测 |
| -------- | -------------------------- | ------------------------------ | ---- |
| A 脏     | 聊天与会话都在             | exit 1，两个面都命中           | ✓    |
| B 净     | 都清干净                   | exit 0，报「0 命中」           | ✓    |
| C 半脏   | 只清聊天                   | exit 1，**只剩会话记录**一个面 | ✓    |
| D 扫不到 | 数据库路径指向不存在的文件 | exit 1，报「不能报告 0 命中」  | ✓    |

C 这一条是关键：它证明两个面**各自独立生效**，不是靠其中一个盖住另一个。

### 3. 缺陷 3：通道审计判不了相对路径逃逸（`channel-audit.mjs`）——这次的「主菜」

旧审计的答案键规则是**子串匹配**，要求写成 `/incident/runs` 这种绝对形态；
越界规则只看绝对路径。于是 Agent 的 cwd 是 `incident/workspace` 时，
`cd ../runs && cat ground-truth/F2.json` 整条命令里**一个绝对路径都没有** →
被判成 `clean`，0 污染 0 越界 → **这一轮照样算有效证据**。
2026-11-02 用合成探针实测：三次相对路径读取（ground-truth / faults / 既往报告）
全部被判 clean。

修法：相对路径按 cwd 解析后判定，答案键目录用**解析后的绝对路径**比对
（`ANSWER_KEY_DIRS` / `ANSWER_KEY_FILES`），`cd` 目标要跟 cwd（踩过一次：
漏跟绝对 `cd` 目标会把工作区内的相对路径解析到仓库外，凭空造一条假越界）。

相对操作数只报三种情况：**读到答案键的内容**（污染）、**只列了答案键的名字**（越界）、
**含 `..` 的上爬**（越界）；散文、通配符、shell 变量不报——
否则 0738Z 会从 9 处越界涨到 17 处，多出来的全是 `find -name "AGENTS.md"`、
`-path "*/node_modules/*"`、`$d/SKILL.md` 这类假阳性。

顺带查出一个**旧脚本漏掉的真污染**（两条，都是相对写法）：

- **10-23 那一轮**：`for f in faults/*; do head -60 "$f"; done` ——
  把答案键目录里每个文件都读了一遍。旧脚本判 clean，新脚本判污染 1。
- **10-26 那一轮**：`head -60 faults/faults.mjs`（走的是仓库搬家前的旧根路径）——
  旧脚本只报了同一次调用里的 `RESUME.md`，漏了这条。
  修法里加了一步：**旧根路径先归一成当前根再判答案键**，
  否则「换条路径访问同一批文件」就是一个后门。

**负对照**（`node incident/runs/channel-audit-control.mjs`，6/6 通过）：
相对逃逸读内容 / 绝对路径读内容 / 旧根路径读内容 → 必须 exit 1；
只列答案键目录名 → 必须 exit 0（列名字不是读到答案）但要报越界；
列完目录又读文件 → 必须 exit 1；工作区内的正常观测 → 必须 exit 0。

### 4. 缺陷 4：审计脚本截断自己的输出

`channel-audit.mjs` 用 `process.exit()` 收尾。stdout 是管道时 `process.exit()` 会**截断**输出：
实测 19911 字节的 JSON 报告经管道只剩 16384 字节，下游 `JSON.parse` 直接炸。
而 `round-table.mjs` 正是用管道调它的，炸了之后旧写法把结果降级成 `{verdict: 'not_run'}`——
`'not_run'` 不是 `'contaminated'`，于是**这一轮照常被算成有效证据**。

修法三处：审计脚本改用 `process.exitCode`（让 Node 自己 flush 完再退）；
`round-table.mjs` 解析失败**直接抛错**（宁可表生成不出来，也不能悄悄放行）；
`leak-scan.mjs` 同样改掉。

### 5. 顺带修的：脱敏件审计不出真结论

脱敏把绝对路径换成了 `<repo>` / `<home>`，而审计的两条规则（绝对路径判定、cwd 跟踪）
都建立在绝对路径上。现在审计认识这两个占位符并还原成真实路径，
**原件与脱敏件的审计结论现在完全一致**（证据件必须能自己复现自己的判定）。
六轮 10-30 的原件/脱敏件对账全部一致（1/4、0/2、0/1、0/6、1/4、0/10）。

`round-table.mjs` 也改成**当场重跑**审计并与 manifest 里存的那份**对账**：
不一致就作废这一轮并写明差在哪，不选边。对账这条已经实测有效
（把 0431Z 的记录改成「污染 7 处」，表里那一轮立刻变「否」，并写出
「审计记录（污染 7 / 越界 1）与当场审计（污染 0 / 越界 1）不一致」）。

### 6. 缺陷 5：我自己引入的误判（`ls` 目录 ≠ 读到答案）

**这一节是今天的教训本身，所以写得最长。**

修好缺陷 3 之后，我把 0738Z 判成了污染，理由是它的 Agent 做过这一条：

```
cd /mnt/.../incident; ls -la agent-profile faults skills 2>/dev/null; ...
```

`ls` 的输出只有 `faults:` 目录下的 `faults.mjs` 与 `load-hammer.mjs` **两个文件名**，
Agent **没有打开过它们**。它当时的推理里写得很清楚：

> 「But `faults/faults.mjs` is the injection script = ground truth. Reading that would be reading
> the answer key. I should avoid reading faults.mjs content in detail to keep the diagnosis honest…
> I'll base the diagnosis on the sanctioned channels.」
>
> 「So I must NOT read incident/faults/faults.mjs or incident/RESUME.md or runs/.
> **I already listed directory names (harmless), but I must not read their contents.**」

也就是说：**它认出了答案在哪，并主动决定不读。** 我的新规则把
`classifyPath()` 判成污染的**条件**从「路径落在答案键上」改成了一刀切——
于是**列出目录名**也变成了污染。

**两个独立的对照证明那是误判**：

1. 人工复核件（`runs/audit-2026-10-30T0738Z.md` §2.5）逐条审过 47 次工具调用，
   独立判定：「目录列表 … **无一读到答案**」，「零污染」，越界 9 次。
   **它与旧脚本一致、与我改完的脚本不一致。**
2. 整个实验台**没有任何一轮**真正读过答案键内容——
   9 份 transcript 全量扫过，`cat`/`head`/`grep`/`sed` 命中
   `faults.mjs`/`ground-truth/*.json`/既往报告的次数是 **0**。

**判据最终定成**：**读到答案键里的内容 = 污染；只列名字 = 越界。**
实现上按**动词**区分（`ls`/`find`/`stat` 只出名字；`cat`/`head`/`grep`/`sed` 出内容；
`find` 带 `-exec` 按读处理），逐段判而不是整条命令判一个模式——
`ls faults` 与 `cat faults.mjs` 必须在同一条命令里分开定级。

**为什么这不是「放水」**：同一个动作写成绝对还是相对，判定必须一致（缺陷 3 的原则不变）；
列名字仍然会被**逐条列为越界**（0738Z 的越界因此从 9 变成 10）；
真的读到内容的照旧判污染——10-23 与 10-26 两轮就是这么被判出来的。
**「读到内容」这条线**也正是 Agent 自己的契约写的口径：
「工作区之外的**文件**不是证据源…读到这些等于提前知道答案」——
契约说的是**文件**，列目录名不是读文件。

**留下的教训**：闸门改口径时，**先找独立对照**（人工复核件）再改。
如果当时先看了 §2.5 那句「无一读到答案」，这次误判根本不会发生。
误报和漏报一样有害——误报会把闸门变成狼来了，真出事时没人再信它。

### 12. 缺陷 7：「审计没跑成」被当成「审计说没问题」——0350Z 的病根还开着

写这一节是因为准备跑下一轮时顺手做了一次 `--dry-run`，
发现**指标表还有一个洞没关**：上一轮修的是「路径解析」和「输出截断」，
但判定逻辑本身还留着一条缝。

**复现方式**（合成 manifest，不碰真实证据件）：

```json
{
  "stamp": "2026-11-02T9999Z",
  "agent": {
    "report": "<repo>/incident/runs/agent-report-2026-10-30T0738Z.md"
  },
  "score": { "path": "<repo>/incident/runs/score-2026-10-30T0738Z.json" },
  "channel_audit": { "verdict": "not_run" }
}
```

这个 manifest **没有 transcript**，所以 `fresh` 是 null，表只能退回去看 manifest 里存的那份
——而 runner 在审计脚本挂掉时写的正是 `{verdict:'not_run'}`。
原判定逻辑是：

```js
valid = 没标无效 && 没判污染 && 对得上 && 有分数;
```

`not_run` 既不是 `contaminated`，也不影响任何一条 → **这一轮被判成有效轮，准确率 1.0 照进表**。

**这就是 0350Z 的病根**：那一轮当时没留通道审计记录，表里「没有污染」=「没有污染」，
它一直在指标表里被算成有效轮。它后来作废，靠的是**后来手工补跑审计**，
不是表自己发现的——表当时根本没这个能力。

**修法**（`round-table.mjs`）：把「审计状态未知」单独拎出来当成无效：

```js
const auditUnknown = !fresh && (!ca || ca.verdict === 'not_run');
```

即：**transcript 解析不出来、且 manifest 里的审计也不是一次真实审计 → 这一轮不算数**，
无效原因写「通道审计状态未知：transcript 解析不出来且审计未跑成」。

### 6. 复核件查出来的**实验室侧**根因（这一条比上面五条都重要）

报告【反对证据】#1 说「实例 A、C 当时 HEAD 是修复提交 `7bb726a`，却仍在报 NPE」，
并把它列为**未解释项**，要求补 CI 构建日志 / 镜像 digest。**这个谜底是实验室自己造的**：

| 实例          | 当时的真实 HEAD                     | 现在 `git log` 里 |
| ------------- | ----------------------------------- | ----------------- |
| A 05:07:14 起 | `486fb57`（0446Z 的注入，05:06:53） | **已删除**        |
| C 07:19:32 起 | `f24ecb8`（0703Z 的注入，07:19:22） | **已删除**        |

两条提交在两轮失败后被删掉并归档进
`~/incident-lab-archive/failed-f2-0446z.bundle`（→ `2fc9d54`）与
`failed-f2-0703z.bundle`（→ `f24ecb8`），所以 0738Z 的 Agent 看到的历史里
那两次「缺陷上线」从来没发生过。它的推断（「跑的不是 HEAD 源码」）在它看到的历史里**必然成立**。

**代价**：报告因此少写了一整个最有价值的模式——**同一个缺陷 blob 被部署 → 修回 → 又被部署回去**。

**纪律**：

- 任何「某个时刻部署了什么」的判断，**先查 `round-manifest-*.json` 的 `injection.at` / `injection.commit`**，
  再决定是不是真的矛盾。`git log` 只能证明「这一轮看到的是什么」。
- **不要**把归档 ref 放回服务仓库：`refs/lab-archive/failed-f2-*` 这个名字本身就泄漏 F2，
  `git log --all` 一看就穿。要保留就只能用中性 ref 名，而那是基准设计决定，不能顺手做。

### 8. 跑 F4 前要做什么

0738Z 收尾时把服务仓库回退到了 `7bb726a`（**判空兜底在位**），这是 F2 的静默态，
不是 F4 的。两者的静默态方向相反：

|                         | 源码                                  | order 2 在压测路径 | 旋钮 | 静默态为什么这样                     |
| ----------------------- | ------------------------------------- | ------------------ | ---- | ------------------------------------ |
| F2 静默态（当前）       | `7bb726a`，兜底在位                   | **在**             | 2000 | 缺陷没上线，压着也只会降级成 UNKNOWN |
| F4 静默态（跑 F4 要的） | **兜底被删掉**（旧链 `072d275` 那种） | **不在**           | 2000 | 缺陷在线但没人踩它；旋钮一改就发作   |

F4 的注入只改旋钮（2000 → 1），代码一行不动——但如果源码里兜底还在，
超时 1 ms 只会让 `fetchProfile` 抛异常、被 catch 成 null、再被兜底成 UNKNOWN，
**order 2 依然 200，不会告警**，这一轮根本起不来。

所以跑 F4 前按顺序做：

1. **让缺陷重新在线**：在新链上再注入一次 F2（`node incident/faults/faults.mjs inject F2`
   会产生一个新提交），或临时检出旧链的 `072d275`。推荐前者——旧链已归档在仓库外，
   检出来会让观察窗里出现「不可解释的历史」。
2. `./lab.sh build target-service` 重建，**源码与镜像必须是同一版**，
   否则 Agent 的 `git diff` 结论和运行时行为对不上，这轮作废。
3. 旋钮回到 `DOWNSTREAM_TIMEOUT_MS=2000`、`LOAD_PATHS` **不含** `/api/orders/2`、
   无告警、5xx = 0。
4. **等窗口**：F4 的 `checkWindow()` 要求 HEAD 已在 15 分钟窗口外。
   如果第 1 步是现注入的，就得再坐稳 16 分钟（`run-round.mjs` 不会替 F4 做 settle，
   它 `settle()` 直接返回 null）。
5. ⚠️ 这一轮的观察窗里会留着第 1 步那次注入的容器活动。**manifest 必须记清 `injection.at`
   和 `injection.commit`**——否则又会重演 L1：Agent 在日志里看见一段解释不了的 500，
   而这只是实验台自己摆场子的动作。

### 4. 判据 v2：四处「量的是排版，不是诊断能力」

10-30 上午那轮 F4 报告，逐条人工读过：机制链完整（读超时 → 客户端产出 null → 未判空 → NPE → 500），

而 v1 的切段只认 markdown 标题 → 六个字段全判 `NO_SECTION`。

四处改动，同一个毛病——**判据量的是排版，不是诊断能力**：

| #   | v1 的问题                                                          | v2 怎么改                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 切段只认 `^#+.*【…】`，Skill 契约里的 ```text 围栏写法一律切不出来 | 按**契约标记**（【根因假设】…）切；标题写法与围栏写法都认。旧实现保留成 `extractSectionsLegacy`，对照过：10-26/10-27/10-30T0423Z 三份报告新旧结果逐字节一致，只有围栏那份从「全空」变成「切出来」 |
| 2   | C2 要求字面「返回…null」，报告写的是「折叠成 `null`」              | 词表扩到 返回/折叠/变成/降级/转成/映射为/归并/产出…null。**负对照**：说了超时+判空+NPE 但从没说客户端产出 null 的报告，C2 仍然 FAIL                                                               |
| 3   | Q3 数「排除」两个字                                                | 改成数**条目**（bullet / 编号项 / 表格数据行）。10-30T0423Z 报告用 6 个 bullet 写了 6 条已排除假设，每条都不带「排除」二字，旧口径只得 2 分                                                       |
| 4   | Q2 只在根因节里找三个固定词                                        | 词表扩到 触发源/触发因/触发因素/触发条件/必要条件/前提条件/前置条件/前置缺陷/放大条件/放大器/放大因子，取全文，且要求**至少两个**不同的层级词（分层归因 = 至少分出两层）                          |

**F2 与 F4 的「发布归因」判据故意不一样**，这不是随手改的：
F4 的真值里**发布就是必要条件**，F2 的真值里**发布就是触发源**。
所以「必要条件 + commit 字样」这种邻近式匹配，对 F4 是对的、对 F2 是**假阳性**
（F2 的报告完全可能写「必要条件：10-26 那次提交删掉了判空兜底」——那是事实，
而且「触发源」是今天那次发布）。⇒ F2 的降级判据改成**主语绑定**
（`发布…不是触发源`），F4 保留宽口径。两种写法都做过正负对照。

改判据的纪律（这轮定下来，以后照办）：
① 先判断是**判据错**还是 **Agent 错**——报告内容满足判据本意但模式没命中，就是判据错；
② 改完必须过 `node incident/runs/calibrate-scorer.mjs`（人工审计过的案例集，含两个交叉案例必须仍是 0.0；
案例集会随轮次增加，**每次改判据时按当时的全量跑**，不能只跑旧的 5 个），
2026-10-30 改 v3 时是 **7/7 通过**（5 个旧案例 + 0738Z + 1 条负对照）；
③ 必须写**负对照**——把判据的实质抽掉的报告，仍然必须判 FAIL；
④ **所有轮次用同一个判据版本重新打分**，分数文件里带 `rubric_version`；
⑤ 新旧分数并列披露。

> ⚠️ 纪律本身也是纪律：**看见分数不对就调判据，等于自己给自己判卷**。
> 所以每条改动都要能说清「为什么这个模式本意就是量这个，而它量错了」，
> 说不出就别改，把报告留着让人复核。

### 5. runner（`incident/runs/run-round.mjs`）的几处修法

一轮 = 一条命令：`node incident/runs/run-round.mjs --fault F4`。每一步的实际输出都落进
`round-manifest-<ts>.json`，指标表里的数字因此有证据链。

| 修法                               | 为什么                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **先打分再恢复**                   | 之前恢复失败会把整个打分跳过，一轮白跑。恢复失败现在只记 `restore.ok=false`，不吞分数                                     |
| **fetch 带 4 次重试**              | 容器刚重建时回环端口会短暂拒连，那是抖动不是台子坏了                                                                      |
| **失败抓 stack**                   | 之前只打 `err.message`，看不到是哪一步挂的                                                                                |
| **F2 静默态要「坐稳」**            | 见下                                                                                                                      |
| **F2 的 settle 取 max 而不是 min** | 旋钮 mtime 与容器启动时刻要**都**滑出 15 分钟窗口，取较早的那个会漏掉「重建比旋钮改动慢」的情况，基线那次部署会卡在窗口里 |
| **`faults.mjs` 用绝对路径**        | 那两步的 cwd 是 `incident/`，相对路径会拼成 `incident/incident/...`（本轮真踩了一次）                                     |

**F2 为什么要坐稳**：F2 的静默态要换代码（提交一次「把判空兜底加回来」+ 重建容器 + 改压测路径），
这三件事各自都是一次「变更」。它们若落在 15 分钟窗口里，
Agent 会看到窗口内既有代码变更又有配置变更（压测路径），
那一轮测的就变成「Agent 能不能在两个变更里挑对」，而不是「Agent 会不会误归因到发布」。
所以静默态摆完要等 ≥16 分钟再注入（`--settle-ms` 可调）。

F4 不需要坐稳：它的触发源就是那一次容器重建本身。

### 服务仓库历史重建（这才是这轮最要紧的动作）

**为什么必须重建**：上一轮残留的那半句
`-- the service degrades a missing profile to ship_to=UNKNOWN.`
是 `data.sql` 里两行种子注释中的一行。它同时出现在两条提交的 diff 里
（`83c26bf` 里被**加上**，`38b3705` 里被**删掉**）——
所以只要链上任何一条提交还在，说"删掉它"的那条提交本身就把答案写在 diff 里了。
**只有整条链重建才能真正清掉**，而这正是 10-27 那轮没做完、只披露没解决的那一项。

**做法**：新增 `incident/runs/rebuild-service-history.mjs`（可复现，有 dry-run）。
用 plumbing 逐条复制原始 commit object，**只改 `tree` / `parent` 两行**，
作者、作者时间、committer、committer 时间、commit message 全部逐字节保留。
唯一被重写的是 1 个基线文件 `target-service/src/main/resources/data.sql`。

脚本内置 4 条断言，任何一条不成立就中止：

1. 重建后 HEAD 的 tree == 旧 HEAD 的 tree（工作区最终内容不能变）。
2. 每条重建提交与对应旧提交的差异，**只**出现在被重基线的文件上。
3. 每条提交 diff 里**每个非重基线文件**的 blob 哈希与旧提交逐一相等。
4. 重建后变空的提交被丢弃（不留下空提交）。
