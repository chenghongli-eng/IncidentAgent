# root-cause-report

**走完流程 ≠ 可以宣布根因。** 这一步负责把"证据"变成"可被挑战的结论"。

## 判定规则

- 每个根因假设**至少有一条证据支撑**。没有证据的猜测不写。
- 证据不足时输出"证据不足"，并写清**还缺什么证据**。这不是失败，比猜错好。
- 走完流程但无收敛 → 允许输出多个候选假设，标明各自置信度与待验证项。

## 报告契约（字段固定，缺一不可）

```text
服务 / 严重级 / 告警起始          ← 来自 alert-triage

【根因假设】
  置信度：0.00-1.00
  机制：<失效机制，一句话>

【支持证据】
  - <证据>  来源：<哪个工具 / 哪条命令>  时间：<时间戳>

【反对证据 / 尚未解释】
  - <反例，或目前无法解释的部分>

【已排除的假设及排除依据】
  - 发布变更：<部署时间 vs 异常时间，差值>
  - 其他：...

【跳过的步骤及原因】
  - <步骤>：<为什么可以跳过，例如"窗口内无代码变更">

【处置建议（仅草案，不执行）】
  - 建议动作 + 命令草案，交人工执行
```

## 置信度锚点

| 区间 | 含义 |
| --- | --- |
| 0.85-1.0 | 机制已确认且有时间对齐证据，反例已解释 |
| 0.6-0.85 | 机制清晰但缺一条独立验证，或有未解释的反例 |
| 0.3-0.6 | 多候选并列，均有部分证据 |
| < 0.3 | **输出"证据不足"，不要写假设** |

## 关于处置建议

**只输出草案，不执行。** 本 Agent 在诊断阶段没有任何写权限，
给出 `kubectl` / `redis-cli` / `docker restart` 之类命令是给人看的，
不是给它自己执行的。命令草案里不要包含真实凭据。

## 关于跳步

跳步是允许的，**沉默跳步不允许**。写清楚跳过了哪步、为什么。
本项目评测里最容易暴露的失败模式是"过度归因到最近一次发布"——
当部署窗口与异常时间对不上时，正确答案是**明确排除发布假设并说明依据**，
而不是继续在 diff 里找一个看起来相关的改动。
