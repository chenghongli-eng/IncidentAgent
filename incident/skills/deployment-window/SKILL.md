# deployment-window

这一���的目的只有一个：**把"时间相关"变成一个可判定的结论**，并给出它成立或不成立的依据。

## 判定规则

设 `T_err` = 日志首次异常时间（来自 `log-triage`），`T_dep` = 最近一次部署/重启时间。

| 条件 | 结论 | 置信度 |
| --- | --- | --- |
| `T_dep ≤ T_err ≤ T_dep + 15min` | 高度相关，继续 `git-diff-analysis` | 高 |
| `T_err > T_dep + 15min` | 相关性弱，**不要**继续查这次部署 | 低 |
| `T_err < T_dep` | 故障先于部署，**排除**该部署 | 排除 |
| 本次故障期间无部署 | 无变更可归因 | — |

## 怎么查部署时间

部署在实验环境里由容器重建产生，因此：

```bash
LAB='node "$INCIDENT_LAB"'

# 容器重建时间 + 应用就绪时刻 —— 这就是 T_dep
$LAB runtime started

# 运行时旋钮的生效值（actuator 会把值全部掩码成 ******，读不到）
$LAB runtime env

# 代码变更：看部署窗口内的提交
$LAB git log --since 2026-10-20T13:00:00 --limit 10
```

`runtime started` 一次给出两个时间：**容器重建时刻**（`container_started_at`）与
**应用就绪时刻**（`app_started_log`）。取哪一个作 `T_dep` 取决于规则口径：
以容器重建为准则故障落在窗口内的程度更宽，以应用就绪为准则更严。
**选定一个口径后全程只用它，并在报告里写明用的是哪一个**——两个时间混用会让
Δ(②−③) 这类差值失去意义。

`runtime env` 只吐实验台的几个旋钮（超时、连接池、负载路径），不吐凭据。
`actuator env` 与 `actuator configprops` 的值全部是 `******`，
**不要**用它们判断配置是否变过，也不需要绕到容器外面去读。

## 输出

```text
最近部署：<时间与 commit> ｜ 与异常首次出现相差 <N> 分钟 ｜ 结论：高度相关 / 相关性弱 / 已排除
```

## 不要做的事

- **这是本项目最容易被跳过的步骤。** 见 `root-cause-report` 的跳步规则：跳过必须写明理由，
  "没找到部署记录"不是理由，"最近一次部署比异常早 40 分钟，因此与本次故障无关"才是。
- 不要因为"这个服务最近发过版"就默认相关。**默认结论是无关**，需要证据推翻它。
